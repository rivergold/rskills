# 模块数据模型边界设计规范

这份规范用于划分模块的核心内部数据模型与对外协议数据模型。

## 分层与职责

每个模块的代码分为**核心**和**业务**两部分：

| 部分 | 职责 |
| --- | --- |
| 核心 | 执行计算、维护内部状态；代码不依赖任何 proto。 |
| 业务 | 承接模块对外输入和输出，并负责协议模型与核心内部模型之间的转换。模块对外输入和输出必须是 proto。 |
| `runtime-proto` | 定义模块间如何理解和交换的对外协议数据模型。 |
| `types` | 在核心确有需要时，定义核心内部使用的数据类型。 |

`runtime-proto` 也会定义位姿、速度、任务等领域概念，并非只定义“传输数据”。区别在于：proto 规定这些概念**如何被其他模块理解和交换**；核心的 `types` 规定模块内部**如何使用它们进行计算和维护状态**。同一个领域概念可以有两种表示，由业务部分负责转换。

## 何时定义核心内部 dataclass

当一个阶段需要把 **3 个及以上的值**一起交给后续阶段，且这些值能组成一个**有明确名称的概念**时，满足以下任一条件，**可以**定义 dataclass：

1. **必须保持一致**：例如属于同一帧、同一时刻或同一坐标系，拆开后容易错配。
2. **要作为整体继续流转**：会经过多个阶段、进入队列或缓存，或交给多个消费者。
3. **位置式传递容易出错**：几个值类型相同，或者单位、含义仅靠参数位置难以辨认。
4. **创建时需要校验约束**：例如尺寸匹配、取值范围或字段之间的关系。

这是决定是否需要内部数据类型的条件，不要求为每个 proto 定义一份对应的 dataclass。

## 同一概念的两种表示如何命名

尽可能保持概念名称相同。同一文件需要同时使用两种模型时，给导入的 proto 类型起别名，让未加前缀的名称指向核心内部类型。

Python 示例：

```python
from protocol import Pose as ProtoPose
from core.types import Pose

def pose_from_proto(msg: ProtoPose) -> Pose:
    return Pose(x=msg.x, y=msg.y)
```

C++ 示例：

```cpp
using robot::core::Pose;
using ProtoPose = runtime_proto::geometry::Pose;

Pose PoseFromProto(const ProtoPose& msg) {
    return Pose{msg.x(), msg.y()};
}
```

## 检查问题

- 核心代码是否直接导入、包含或以其他方式依赖 proto？
- 模块对外输入和输出是否由业务部分使用 proto 表达？
- 协议模型与内部模型的转换是否位于业务部分？
- 新的内部 dataclass 是否满足上面的定义条件？
- 同一概念的两种类型是否尽量同名，并在同文件使用时消除歧义？
